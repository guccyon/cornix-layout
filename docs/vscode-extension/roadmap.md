## v0.2 の position_map

`position_map.yaml` のキーの名前は、ふつうは利用者のキーボードのキーキャップに印字されている文字（物理キーのラベル）を想定している
（Cornix では無刻印のキャップを使う人もいる）。割り当てた論理キーとは別のものなので、画面では色を分けて見せる。
v0.1 ではメタデータの節での表示を外した（欄の名前としてだけ使う）。v0.2 では次をまとめて入れた（利用者からの申し送り）。
決めたのは、図の上のトグルボタンで固定の切り替え＋ Alt を押している間だけ一時表示、名前は紫、マクロの `M` の印は橙に変える、の形
（[tasks-v0.2.md](tasks-v0.2.md) の決めたことの 1）。下は決める前の申し送り。

- 名前（レイヤーの欄のラベル）を画面から編集する
- キーボード図で、割り当てたキーの代わりに position_map の名前を見せる表示を足す（呼び方は「位置の名前」「キーの名前」など、決めるときに選ぶ）
  - 切り替え方: マウスを載せている間、クリックでの切り替え、図にフォーカスがあるときに Space を押している間
  - 名前の文字は、位置の名前だと分かる色（紫など）にする
  - 下のペインのレイヤーの編集画面の欄のラベル（位置の名前）も同じ色にする
- 決めるときの注意
  - 図のキーはボタンなので、フォーカスのあるキーで Space を押すとそのキーのクリック（下の欄へ移る）になる。
    Space を使うなら keydown で既定の動作を止めるか、別のキー（Alt など）にするかを決める
  - マクロの印 `M` がすでに紫（`--vscode-charts-purple`）。位置の名前を紫にするなら、印の色を変えるか、
    印・帯・窓で使っていない色（TD の窓の茶、★ の緑、M の紫、帯の青以外）から選ぶ

## v0.3 への申し送り（v0.2 を使って気づいたこと）

2026-10-20 に 0.2.0 の .vsix を入れて試したときの利用者からの申し送り。**すべて v0.3 で入れた**（[tasks-v0.3.md](tasks-v0.3.md) の「v0.3 で入れるもの」の 1〜8）。
選んだ形: コンボは番号のボタンで 1 つずつ強調（決めたことの 1）、同梱のショートカットは候補の一覧の下の「同梱から選ぶ…」から階層の選択を開く（決めたことの 2）。
下は決める前の申し送り。

- **位置の名前**
  - 「位置の名前」のトグルボタンにマウスを載せている間も、図に位置の名前が出ない。載せている間は出す
  - 名前の出所が `position_map.yaml` であること、そこを変えると名前（ラベル）を変えられることを、画面のどこかで分かるようにする
- **プレビュー（キーボード図）**
  - `Up` / `Left` / `Right` / `Down` は `↑` / `←` / `→` / `↓` で見せる
  - キーの割り当てを解除すると、図のキーそのものが消える。`KC_NO`（NoKey）のときと同じ見た目（枠はあって中は空白）にする
  - コンボを図で見せる。案は 2 つで、決めるときに選ぶ
    - コンボ用のトグルボタンを置き、押すかマウスを載せている間、コンボのキーを枠線などで強調する。同じコンボは同じ色にする
      （数が多いとごちゃごちゃして見えるかもしれない）
    - コンボの番号のボタンを並べ、押すかマウスを載せている間、そのコンボだけを強調する。同時に選べるのは 1 つだけ
- **編集の欄**
  - 割り当てを解除した欄に出る `（なし）` は出さず、空白のままにする（多言語化するときに邪魔になる）。
    今は `layerEditor.ts` などの入力欄の placeholder が `（なし）`
  - 最初に開いたとき、レイヤー以外の節（マクロ・タップダンス・コンボ・ショートカット・QMK 設定など）は畳んでおく。
    畳んでいることが分かるように `▶` / `▼` の印を付ける
- **同梱のショートカット**: `Shortcut('…')` を割り当てたくても、どんなショートカットが同梱されているかが分からない。
  一覧を見て選べる導線を作る（候補の種類で絞る、一覧の画面を開く、など。決めるときに選ぶ）

## 将来の拡張（版を決めていない）

- **TypeScript 版のサーバー（B 案）**: 母艦以外でも補完と説明を使えるように。Ruby が見つかれば Ruby、なければ同梱の TypeScript。
  前提: `MO(n)` など関数形式の一覧を `KeycodeCodec` の定数から `data/` へ出す。B では compile を使う検証はしない
- **テキストエディタの補完（LSP）**: 同じバックエンドを使う別の入口。Neovim などでも使える
- **自分のショートカットのアイコン**: `shortcuts.yaml` の書式を広げるときに `icon:` などを足す
- **Marketplace での公開**: そのときはアイコンの商標の扱いを見直す
- ~~**実機への書き込み**~~: v0.4 で入れた（反映のプレビュー → 確定。[tasks-v0.4.md](tasks-v0.4.md)、ADR 018・019・020）
- **実機の内容を選んで取り込む（マージ）**: 別のマシンで cornix を変えてプロファイルのコミット・プッシュを忘れたとき、別のマシンでつないで実機の今の内容とそのマシンのプロファイルを比べ、
  違いを選んでプロファイルに取り込む。バックアップから戻す（リストア）よりも、衝突を解くマージに近い（Tetsuro、2026-10-22）。下の pull と一緒に考える
- **実機から取り込む（pull）**: 実機の状態をプロファイルに取り込む。decompile が設定を書き直すので、注記・コメント・未保存の変更との関係を決めてから
- **マトリクステスター**: 押したキーを図で光らせる（配線・チャタリング・位置の名前の確認）。RMK 0.8 ではロックの解除が要る（[device.md](../device.md) の「アンロック」）
- **物理キーを押して割り当てる**: 欄を選んで手元のキーボードのキーを押すと、そのキーが入る
- **マクロの記録**: キーを打って手順を記録する
- **Key Override と Alt Repeat Key**: 今は .vil の中身を解釈せずに運ぶだけ。RMK がどこまで対応しているかを確かめてから
- **別リポジトリへの切り出し**: 大きくなったら `git subtree split`

## v0.1 の進め方

最初にリクエストの約束を文書で決め、Ruby 側と画面側をその約束に沿って作った（v0.1 の記録。実際の分け方と PR は [tasks.md](tasks.md)）。

1. このドキュメントをリポジトリの `docs/vscode-extension/` に置き、リクエストの約束（メソッド名・引数・戻り値・エラー）を文書にする（[protocol.md](protocol.md)）
2. Ruby: 常駐のサブコマンドと JSON-RPC の土台（MCP サーバー `Interface::Mcp` の標準入出力の扱いを参考に）。位置づけは Interface 層、中身は Application 層のユースケース（[architecture.md](../architecture.md) の依存の向きを守る）
3. Ruby: プロファイルを構造で読む（レイヤー・位置・表示ラベル・アイコン ID）
4. Ruby: 候補を引く（項目の種類ごとの候補と並び順）と、「この入力ならこの候補」の共通テストのデータ
5. Ruby: 保存前の状態での検証と、変わった値だけを書き換える変更（「どのファイルのどこをどう変えるか」を返す）
6. `data/` にアプリ名 → アイコン ID の対応表と、全アプリに対応があるかのテスト。`data/qmk_settings.yaml` に説明文
7. 拡張: `editors/vscode/` の土台（esbuild、バックエンドの起動と接続、`cornix.path`、コマンドとアクティビティバー）
8. 拡張: キーボード図とレイヤーの編集画面、キー入力欄、アイコン（SVG とライセンス表記を同梱）
9. 拡張: dirty と Ctrl+S、外での変更の読み直し、QMK 設定、メタデータの表示
10. CI を変更したパスで Ruby と Node に分ける。.vsix を作って手元で入れ、自分のプロファイルで確かめる

守ること: リポジトリの `.claude/CLAUDE.md` の開発ルール（日本語、RSpec が全部通る、README の同期、PR の説明の形、実機に書き込まない）。
